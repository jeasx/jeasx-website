## 2026-11-02 - Jeasx 3.0.0 released

> **The promise you made.** Await anything, stream everything.

🚀 Jeasx 3 streams your pages. JSX is now sent to the browser while it is
still rendering, powered by `jsx-async-runtime@3`, which also renders about
2x faster than v2. This release also hardens request routing, the build and
the dev server.

There are breaking changes in Jeasx and in `jsx-async-runtime`. Each one has
a migration recipe below. Most projects only need these steps:

1. Replace `{{ html: "..." }}` with `{html("...")}`.
2. Replace `class`/`style` objects with strings.
3. Move `this.errorHandler` to `setErrorHandler` in `jeasx.config.js`.
4. If your `responseHandler` changes the HTML, read the stream into a string first.

👀 Want to see it in action? [Jeasx Expo](https://expo.jeasx.dev) has many
new examples that show off the new features, e.g.
[Streaming HTML](https://expo.jeasx.dev/streaming),
[Out-of-order streaming](https://expo.jeasx.dev/out-of-order) and
[Server-Sent Events](https://expo.jeasx.dev/sse).

### 💥 Breaking changes in Jeasx

#### JSX responses are streamed, so `responseHandler` gets a stream

Pages are rendered with `jsxToStream` instead of `jsxToString`. The browser
gets the first bytes while slow parts of the page (e.g. awaited data) are
still rendering. For JSX, the `payload` passed to `this.responseHandler` is
now a `ReadableStream<string>` instead of a `string`.

**Migration:** if your `responseHandler` only sets headers or passes the
payload through, nothing changes. If it changes the HTML (e.g. to format or
minify it), read the stream into a string first:

```js
this.responseHandler = async (payload) => {
  if (payload instanceof ReadableStream) {
    payload = (await Array.fromAsync(payload)).join("");
  }
  return typeof payload === "string" ? format(payload) : payload;
};
```

Pages that are post-processed this way are not streamed.

#### `this.errorHandler` was removed

Errors thrown by routes and guards now go to Fastify's error handler. Jeasx
no longer looks for `this.errorHandler`.

**Migration:** register an error handler in `jeasx.config.js`. It runs for
errors from all routes:

```js
// jeasx.config.js
export default {
  FASTIFY_SERVER: (fastify) =>
    fastify.setErrorHandler(async (error, request, reply) => {
      request.log.error(error);
      reply.status(error.statusCode ?? 500).type("text/html; charset=utf-8");
      return "<h1>Something went wrong</h1>";
    }),
};
```

Without your own handler, Fastify answers with a JSON error. `jeasx.config.js` is not compiled by esbuild by default, so it can't contain JSX. If you want JSX in your config, write it as `jeasx.config.jsx` and compile it with your own npm script:

```sh
esbuild jeasx.config.jsx --bundle --packages=external --outfile=jeasx.config.js --platform=node --format=esm --jsx=automatic --jsx-import-source=jsx-async-runtime
```

**Errors while streaming:** the error handler only runs for errors thrown
before the first chunk is sent, e.g. in a guard or before the route returns
its JSX. Once streaming has started, the status and headers are already sent,
and an error thrown by an async component cuts the page off. Wrap risky
components in an error boundary that renders them to a string first:

```jsx
import { html, jsxToString } from "jsx-async-runtime";

async function ErrorBoundary({ fallback, children }) {
  try {
    return html(await jsxToString.call(this, children));
  } catch (error) {
    this.request.log.error(error);
    return fallback;
  }
}

<ErrorBoundary fallback={<p>This section could not be loaded.</p>}>
  <RiskyComponent />
</ErrorBoundary>;
```

See [Catch errors](https://expo.jeasx.dev/error-handler) for all three cases.

#### `request.path` is decoded

`request.path` is now URL-decoded, e.g. `/caf%C3%A9` becomes `/café`.
Backslashes become slashes, and repeated slashes are collapsed (`//a//b`
becomes `/a/b`).

**Migration:** remove `decodeURIComponent(request.path)` from your routes.
Decoding twice fails for paths that contain a `%`. Use `request.url` if
you need the raw path.

#### The dev server only listens on `localhost`

`jeasx dev` binds to `localhost`, so other machines on your network can't
reach it. `jeasx start` still listens on all interfaces (`::`).

**Migration:** if you run `jeasx dev` in a container or VM, or test from
another device, set `HOST`:

```sh
HOST=:: npx jeasx dev
```

#### Missing imports in routes are errors

Before, if a route imported a module that doesn't exist, the route was
skipped as if it didn't exist (usually ending in a 404). Now the error is
thrown, so you see the real cause.

**Migration:** fix or remove the import that is reported.

#### Changed responses

- If no route answers and there is no `[404]` route, the response is a
  `404` instead of an empty `200`.
- Objects returned by guards are only used as props. They are never sent as
  the response, even if no route answers.
- Static files are only served for `GET` and `HEAD`. Other methods (e.g. a
  `POST` to `/form`) go to your routes, even if a file with that path exists.
- If a static file is missing or ignored (e.g. a dotfile), `[...path]` and
  `[404]` routes answer instead of the plain error page of `@fastify/send`.
- A `ReadableStream` or Node.js stream returned without a content type is
  sent as `text/html; charset=utf-8`, like strings and buffers.

**Migration:** set a status code or content type explicitly where you
relied on the old behavior. For example, register a Fastify route in
`FASTIFY_SERVER` for non-`GET` requests to a static file.

#### `FASTIFY_SEND_OPTIONS.root` is always the project directory

Jeasx passes file paths relative to the project directory, so a custom
`root` broke file serving. It is now always set to the project directory.

**Migration:** remove `root` from `FASTIFY_SEND_OPTIONS`.

#### `dist` is cleaned before every build

`jeasx build` and `jeasx dev` delete `dist` before building. This removes
outputs of deleted routes, which could otherwise still be served.

**Migration:** don't put files into `dist` by hand. Use `public` instead.

### 🔒 Security

- **Compiled routes were exposed in development:** server routes
  (e.g. `/[index].js`), their sourcemaps and other outputs could be fetched
  from `dist` as static files. This exposed server-side code. They are no
  longer served, including Windows tricks like `/[index].js.` or
  `/[index].js::$DATA`.
- **Special routes can't be requested by name:** requests like `/[index]`,
  `/[...guard]`, `/[...path]` or `/[--metadata--]` no longer call these
  routes directly. The check ignores case, because case-insensitive file
  systems (macOS, Windows) would otherwise resolve `/[--METADATA--]`.
  `/a/404` is still answered by `/a/[404]`.
- **Malformed paths are rejected:** paths with invalid URL encoding, null
  bytes or `.`/`..` segments are rejected with `400`. Repeated slashes are
  collapsed, so `//evil.com` can't be mistaken for another host
  (e.g. in a `<base>` tag).
- **Route and file lookups ignore inherited keys:** a path like
  `/constructor` no longer matches properties of `Object.prototype`.
- **Fewer leaked file handles:** file streams are closed when the response
  ends or is aborted. This includes routes that send a stream with
  `reply.send()`.
- **In production, other outputs of server routes aren't static files:**
  CSS or other files that esbuild writes for server routes
  (e.g. `[index].css`) are no longer served. Before, only sourcemaps were
  skipped.

### ✨ New features

- **Async config options:** all options in `jeasx.config.js`
  (`ESBUILD_SERVER_OPTIONS`, `ESBUILD_BROWSER_OPTIONS`,
  `FASTIFY_SERVER_OPTIONS`, `FASTIFY_SEND_OPTIONS`) and `FASTIFY_SERVER`
  can be async. You can import build-only plugins lazily, so they aren't
  loaded in production:

  ```js
  export default {
    ESBUILD_BROWSER_OPTIONS: async () => ({
      plugins: [(await import("esbuild-sass-plugin")).sassPlugin()],
    }),
  };
  ```

- **Dotfiles in production:** files like `public/.well-known/security.txt`
  are now part of the production build. Whether they are served depends on
  the `dotfiles` option of `FASTIFY_SEND_OPTIONS` (default: ignored), the
  same as in development:

  ```js
  export default {
    FASTIFY_SEND_OPTIONS: () => ({ dotfiles: "allow" }),
  };
  ```

- **Graceful shutdown:** the server closes on `SIGINT` (Ctrl+C) and
  `SIGTERM` and then exits. It stops cleanly in containers (where Node runs
  as PID 1) and while the esbuild watcher is running. Press Ctrl+C a second
  time to kill it if the shutdown hangs.

### 🛠️ Fixes

- `jeasx dev` waits for the first build before starting the server, so the
  first requests don't fail on an empty `dist`. Build errors are logged and
  the watcher keeps running.
- If a file exists in both `dist` and `public`, `dist` wins in production,
  as it does in development. Symbolic links are skipped in production builds.
- Config, routes and metadata are imported with `pathToFileURL`, which
  fixes paths on Windows and paths with special characters.
- A directly requested `/a/404` page keeps its status only if it is answered
  by `/a/[404]`. If a parent `[404]` route answers, the status is `404`.
- File paths with special characters (e.g. `#` or `%`) are served correctly.
- esbuild no longer forces colored output, so logs in CI and log files
  don't contain color codes.
- The docs in `env.js` explain the load order: a variable that is already
  set is never overwritten, and `NODE_ENV` must come from the environment.

### 📦 Updates to `jsx-async-runtime@3.0.0`

Jeasx depends on `jsx-async-runtime` for all rendering, so these changes
affect every Jeasx project. See the
[full changelog](https://github.com/jeasx/jsx-async-runtime/blob/main/CHANGELOG.md)
for every detail.

#### 💥 Breaking changes

**Raw markup needs `html()`**

`{{ html: "..." }}` objects render nothing. This closes an injection path,
e.g. through parsed JSON with an `html` key.

```jsx
// Before
<>{{ html: "<!DOCTYPE html>" }}</>;

// After
import { html } from "jsx-async-runtime";
<>{html("<!DOCTYPE html>")}</>;
```

**Escaping can't be turned off**

`this.jsxEscapeHTML = false` was removed.

**Migration:** wrap trusted markup in `html()`. To pass trusted text through
unescaped everywhere, use a `this.jsxToString` override that returns it as is.

**`class` and `style` must be strings**

Objects and arrays are no longer converted. They render as JSON, like other
attributes, and TypeScript only accepts strings.

```jsx
// Before
<div class={["card", { active }]} style={{ color, "font-size": "2em" }} />;

// After (e.g. with clsx)
import clsx from "clsx";
<div class={clsx("card", { active })} style={`color: ${color}; font-size: 2em`} />;
```

**Components get `children` as written**

As in React, a single child is passed as is, several children as an array,
and there is no `children` prop without children. Before, `children` was
always a flattened array without `null` and booleans.

**Migration:** most components that only render `{children}` keep working.
If you call array methods on `children`, normalize it first:

```jsx
function List({ children }) {
  return (
    <ul>
      {[children ?? []].flat().map((child) => (
        <li>{child}</li>
      ))}
    </ul>
  );
}
```

Generators passed as children are read at render time, so they can only be
rendered once.

**Other breaking changes**

- **Text is plain values:** text children are strings, numbers or bigints
  instead of `{ type: "textNode", text }`. The `textNode` type was removed.
- **Only real elements render:** hand-built objects like
  `{ type: "tag", tag: "b", props }` render nothing. Use `createElement`
  instead. Copies of real elements (`{ ...element, tag: "i" }`) still render.
- **Invalid component types throw:** a tag that is neither a string nor a
  function (e.g. `undefined` from a missing import) fails with a `TypeError`
  instead of rendering nothing. With the Jeasx error handling above, you now
  see these errors.
- **`jsxToString` can return synchronously:** it returns
  `string | Promise<string>`. `await jsxToString(...)` keeps working.
- **Void tags ignore children:** `<br>text</br>` renders `<br>`.
- **Override scope:** a `this.jsxToString` override set by a component also
  applies to the siblings that follow it.
- **Exports:** the `Tag` type was renamed to `ElementNode`. `jsxsDEV` was
  removed from `jsx-async-runtime/jsx-dev-runtime`.
- **Stricter types:** `aria-*` attributes no longer accept booleans, and
  `contenteditable`, `spellcheck`, `translate` and `writingsuggestions` no
  longer accept `false`. Use strings like `aria-hidden="true"` or
  `spellcheck="false"`. Add custom elements to `JSX.IntrinsicElementAttributes`
  instead of `JSX.IntrinsicElements`.

#### ✨ New features

- **`jsxToStream`** renders to a `ReadableStream<string>`. Jeasx uses it for
  all JSX responses. It sends what is rendered so far whenever rendering
  waits for async work, splits large pages into ~16 KB chunks, waits for
  slow clients and stops when the client disconnects.
- **`isJsxNode`** checks whether a value is an element or `html()` markup
  and narrows the type in TypeScript.
- **More child types:**
  - Promises: `<div>{fetchUser()}</div>`
  - Iterables: `Set`, generators, `map.values().map(...)`
  - Async iterables: async generator components and `ReadableStream`,
    rendered in order as items arrive
  - Bytes (`Uint8Array`, `Buffer`) as escaped UTF-8 text:
    `<pre>{response.body}</pre>`
  - Objects with their own `toString` (`Date`, `URL`, `Error`, your classes)
    as escaped text
  - Functions as render props:
    `<Loader>{(data) => <p>{data}</p>}</Loader>`
- **Promise attributes:** `<img src={loadImageUrl()} />`. All promise
  attributes of a tag are awaited in parallel.
- **Better types:** async components with a `Promise<JSX.Element>` return
  type, `key` on every component, `null` attributes, and JSX types for
  `"jsx": "react-jsxdev"`.

#### 🔒 Security

- Only markup created by `html()` is rendered raw.
- Elements carry a Symbol marker, so JSON look-alikes such as
  `{"type":"tag","tag":"script",...}` render nothing.
- Attribute names with whitespace, quotes, `<`, `>`, `/`, `=`, `&` or control
  characters are skipped, and so are invalid tag names (with their children).
  Valid names like `onmouseover` or `script` still render, so allowlist
  attributes and tags that come from untrusted input.
- Keys inherited from a polluted `Object.prototype` are ignored.

#### 🛠️ Fixes

- Rejected promises in props no longer crash Node with an unhandled
  rejection. The error goes to the render.
- Streams that are never rendered (e.g. in a void tag or after a failed
  render) are closed, so they don't keep connections or files open.
- Functions and symbols in attributes are skipped. Event handlers no longer
  print their source code.
- `key` is never rendered, and components don't receive it in their props.
- `createElement` no longer modifies the props you pass in.
- Rendering without a context gives each render its own empty context, so
  data no longer leaks between renders.
- `escapeEntities` converts non-strings with `String()` before escaping.

Dependency updates: `jsx-async-runtime@3.0.0`, `@types/node@26.6.6`

## 2026-08-04 - Jeasx 2.10.0 released

### 🎉 `BUILD_TIME` moved to userland

As part of my ongoing goal to move features from the core into userland, I’ve removed the core-level `BUILD_TIME` variable. While this simplifies the core, I want to ensure your builds aren't affected. If you use `BUILD_TIME` for cache busting, you can now let `esbuild` handle it directly using the powerful [define option](https://esbuild.github.io/api/#define) in your `jeasx.config.js`:

```js
/** @type {() => import("esbuild").BuildOptions} */
ESBUILD_SERVER_OPTIONS: () => ({
  define: { "process.env.BUILD_TIME": `"${Date.now().toString(36)}"` },
});
```

This configuration replaces all references to `process.env.BUILD_TIME` with a Base36 (a-z0-9) encoded timestamp as string (note the additional quotes above).

I have also removed the automatic provision of `BROWSER_PUBLIC_` environment variables to frontend bundles. This gives you the freedom to define your own schema; simply add the appropriate define option to `ESBUILD_BROWSER_OPTIONS` to specify which variables should be available to the frontend.

Dependency updates: `fastify@5.11.2`

## 2026-07-17 - Jeasx 2.9.0 released

### ✨ Less is more... trimming the fat

This release **removes** `@fastify/formbody`, `@fastify/cookie`, and `@fastify/multipart` as core dependencies. Since Jeasx is capable of powering serious, real-world projects without these dependencies, removing them keeps your project's footprint as small as possible. This allows you to enable them individually, only when your specific use case requires them.

- **Forms:** Install `@fastify/formbody` if your project requires _POST_ form support.
- **Cookies:** Install `@fastify/cookie` if you need to handle HTTP cookies.
- **Uploads:** Install `@fastify/multipart` if your project handles file uploads.

Jeasx is built on the philosophy of providing a powerful core while pushing customizations to the user level. By avoiding opinionated defaults, Jeasx gives you the freedom to build a setup that is uniquely your own.

Need these features? No problem! Jeasx makes it easy to customize your stack. To get back to the exact setup from previous releases, just add these dependencies directly to your project:

```bash
npm install @fastify/formbody @fastify/cookie @fastify/multipart
```

Next, update your `jeasx.config.js` with the following configuration to customize your Fastify server instance:

```js
/** @type {(fastify: import("fastify").FastifyInstance) => import("fastify").FastifyInstance} */
FASTIFY_SERVER: (fastify) =>
  fastify
    .register(import("@fastify/formbody"), {/* insert options from FASTIFY_FORMBODY_OPTIONS */})
    .register(import("@fastify/multipart"), {/* insert options from FASTIFY_MULTIPART_OPTIONS */})
    .register(import("@fastify/cookie"), {/* insert options from FASTIFY_COOKIE_OPTIONS */});
```

Because plugins like `@fastify/cookie` and `@fastify/multipart` extend the `request` and `reply` objects, you should add the following imports to `src/types.d.ts` (or a similar definition file in your project) to ensure proper TypeScript support for your editor:

```js
import "@fastify/cookie";
import "@fastify/multipart";
```

This release also removes the additional encapsulation context from the Fastify initialization. This change allows for a more direct and flexible customization of the underlying Fastify instance.

Dependency updates: `jsx-async-runtime@2.2.0`, `@types/node@26.1.1`

## 2026-07-03 - Jeasx 2.8.0 released

### 🚀 Unified Asset & Route Handling

This release completes the architectural transition of merging dynamic server routes and static browser assets into a common directory tree. While Jeasx 2.6 removed the strict directory separation, this version further unifies how these files are processed.

Previously, browser assets were served directly by `@fastify/static`, while server routes were handled by the route handler. This created a limitation where server-side logic (like authentication or custom headers) couldn't be applied to static assets.

With this release, all files - regardless of type - are now handled directly by the route handler. This introduces several major improvements:

- **Enhanced Control:** You can now use guards to modify responses for static assets, such as adding security headers or implementing password protection.

- **Hot-Reloading for Assets:** Static files in development mode are now picked up instantly. No application restarts are required to make new files accessible.

- **Production Optimization & Security:** In production, static files are mapped into a metadata export at build time. This improves server startup performance by eliminating file globbing and provides robust protection against path traversal attacks.

#### ⚠️ Important Migration Note

To achieve these improvements, `@fastify/static` has been removed as a direct dependency in favor of `@fastify/send`. Since `@fastify/static` relied on `@fastify/send` internally, this change provides more flexibility while maintaining the same functionality with fewer dependencies.

A minor configuration change is required to make your application work as expected. You'll need to change references in `jeasx.config.js` from `@fastify/static` to `@fastify/send` .

```js
// BEFORE
   /** @type {() => import("@fastify/static").FastifyStaticOptions} */
   FASTIFY_STATIC_OPTIONS: () => ({/* configuraton options */}),

// AFTER
   /** @type {() => import("@fastify/send").SendOptions} */
   FASTIFY_SEND_OPTIONS: () => ({/* configuraton options */}),
```

## 2026-05-08 - Jeasx 2.6.0 released

🎉 Back in the early days, Jeasx enforced a strict separation between browser and server code. This meant developers had to organize their projects into specific directories like `browser` and `routes`. Over time, this limitation was lifted, allowing for more flexible project structures. While you could freely arrange your application code in the `src` directory, the `dist` directory still maintained the separation between browser and server files.

This created a significant challenge: [esbuild loaders](https://esbuild.github.io/api/#loader) (such as those for importing files or using CSS modules) couldn’t be applied to server routes. The reason? Assets generated for the server and stored in `dist/server` were inaccessible to the browser, making it impossible to leverage these powerful tools in server-side code.

Here are the good news: everything in the `dist` folder is now organized exactly as you’ve structured your application, hard coded sub-directories for `browser` and `server` are gone for good. All files in the `dist` directory are delivered directly to the browser via `@fastify/static`, except the code for server routes (JavaScript files enclosed in square brackets) - this code is still handled on the server. Now you are free to utilize esbuild loaders for your routes and enjoy all the advanced esbuild configurations for bundling server-side code.

### ⚠️ Required updates to `.env.js`

Previously, common browser asset extensions (e.g., `.ttf, .woff2, .svg, .jpg`) were automatically treated as `external` by Jeasx. This meant they were excluded from the bundling process by esbuild. For example, font files or icons stored in the `public` directory and referenced in your bundled CSS files would not be processed by esbuild.

Now, no extensions are marked as `external` by default anymore. If your build fails with an error like `ERROR: No loader is configured for ".woff2"`, you’ll need to explicitly mark the missing extensions as `external` in your `.env.js` configuration by updating the `ESBUILD_BROWSER_OPTIONS`.

Also Jeasx no longer sets a default value for the esbuild `target` option. I recommend configuring it explicitly based on your project’s needs. If you don’t specify a value, esbuild will default to `esnext`.

The example below restores the former esbuild settings used by Jeasx, ensuring a smooth transition to the current release.

```js
/** @type {() => import("esbuild").BuildOptions} */
ESBUILD_BROWSER_OPTIONS: () => ({
  // It’s best to start with an empty list and
  // only add extensions that cause build errors.
  external: [
    "*.avif",
    "*.gif",
    "*.jpg",
    "*.jpeg",
    "*.png",
    "*.svg",
    "*.webp",
    "*.eot",
    "*.ttf",
    "*.otf",
    "*.woff",
    "*.woff2",
  ],
  target: ["chrome130", "edge130", "firefox130", "safari18"],
});
```

After the update, you should start using the [esbuild loader](https://esbuild.github.io/api/#loader) to handle assets. To help you get started, here’s an example of how you can import images directly in your server routes. Simply configure the `file` loader for `.jpg` files in your `.env.js` file:

```js
/** @type {() => import("esbuild").BuildOptions} */
ESBUILD_SERVER_OPTIONS: () => ({
  loader: { ".jpg": "file" },
});
```

You can now import an image located next to your server route and reference it in your code. This way esbuild automatically hashes the image path, so you don’t need to manually update references - even with caching headers applied.

```jsx
import Image from "./image.jpg";

export default function () {
  return (
    <figure>
      <img src={Image} alt="Example image" />
    </figure>
  );
}
```

If you encounter a TypeScript warning for the import, you can resolve it by adding a definition file (e.g., `jpg.d.ts`) to specify the correct typing.

```ts
declare module "*.jpg" {
  const content: string;
  export default content;
}
```

## 2026-02-20 - Jeasx 2.4.0 released

🎉 This release is both a step forward and a step back: the recently introduced support for MDX has been removed from the core project. Jeasx aims to keep its core as lean as possible, so this change aligns with the project's overall goals. Since MDX is not essential for every Jeasx website or application, it makes sense to move it out of the core.

Another key goal of Jeasx is to empower users to implement their own custom solutions in userland, providing the right tools to do so. In short, while MDX remains a fantastic technology for content-driven websites, Jeasx now lets you configure MDX support yourself through a much improved configuration system for its base technologies like esbuild and Fastify.

For esbuild, two new configuration options are available: `ESBUILD_SERVER_OPTIONS` and `ESBUILD_BROWSER_OPTIONS`. These can be defined as functions in `.env.js` that return additional configuration settings for esbuild.

Why use functions instead of plain objects for the configuration? Because using functions allows configurations to be created lazily - only when needed - which is especially helpful for more complex setups over time.

If you want to use MDX with Jeasx, simply run `npm install @mdx-js/esbuild` and add the configuration below to `ESBUILD_SERVER_OPTIONS` in `.env.js`.

If you've used `ESBUILD_BROWSER_TARGET` in the past, you have to move this configuration to `ESBUILD_BROWSER_OPTIONS` as shown below.

```jsx
import mdx from "@mdx-js/esbuild";

export default {
  /** @type {() => import("esbuild").BuildOptions} */
  ESBUILD_SERVER_OPTIONS: () => ({
    plugins: [
      mdx({
        development: process.env.NODE_ENV === "development",
        jsxImportSource: "jsx-async-runtime",
        elementAttributeNameCase: "html",
        stylePropertyNameCase: "css",
      }),
    ],
  }),

  /** @type {() => import("esbuild").BuildOptions} */
  ESBUILD_BROWSER_OPTIONS: () => ({
    target: ["chrome130", "edge130", "firefox130", "safari18"],
  }),
};
```

The existing configuration options for Fastify (such as `FASTIFY_SERVER_OPTIONS`, `FASTIFY_COOKIE_OPTIONS`, `FASTIFY_MULTIPART_OPTIONS`, `FASTIFY_STATIC_OPTIONS`) now require a minor change: they must be defined as functions instead of plain objects.

Additionally, you can now customize the Fastify server instance using the optional `FASTIFY_SERVER` function. This function receives the created server instance and should return the modified version. This feature is especially useful when integrating existing Fastify plugins like `@fastify/compress`, as demonstrated below.

```jsx
import fastifyCompress from "@fastify/compress";

const NODE_ENV_IS_DEVELOPMENT = process.env.NODE_ENV === "development";

export default {
  /** @type {(fastify: import("fastify").FastifyInstance) => import("fastify").FastifyInstance} */
  FASTIFY_SERVER: (fastify) => fastify.register(fastifyCompress),

  /** @type {() => import("fastify").FastifyServerOptions} */
  FASTIFY_SERVER_OPTIONS: () => ({
    disableRequestLogging: NODE_ENV_IS_DEVELOPMENT,
    bodyLimit: 1024 * 1024,
  }),

  /** @type {() => import("@fastify/static").FastifyStaticOptions} */
  FASTIFY_STATIC_OPTIONS: () => ({
    immutable: !NODE_ENV_IS_DEVELOPMENT,
    maxAge: NODE_ENV_IS_DEVELOPMENT ? 0 : "365d",
  }),
};
```

Another notable change is that the fallback content-type (`text/html`) for routes is now set as late as possible. This means you can return plain JavaScript objects from routes, which will be automatically sent as `application/json` by default - without needing to explicitly specify the content-type in your code. This update brings Jeasx in line with Fastify’s default behavior.

Additionally, you can now define routes directly from simple `*.json` or `*.txt` files - perfect for creating static endpoints like a health check or a `robots.txt` file right in your routes folder.
